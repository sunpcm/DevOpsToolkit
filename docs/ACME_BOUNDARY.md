# AcmeConfig 维护边界决策

日期：2026-09-23。状态：**方案确定，迁移未执行**。本文件不改变 `AcmeConfig/` 当前的实验状态，
也不授权真实 CA、生产主机、GitHub 仓库或 Release 操作。

## 现状依据

- `AcmeConfig/` 有独立的 CLI、Python 管理器、systemd 单元、logrotate 与 VM/单元测试；
  需要 root 初始化、专用 `acme` 用户、DNS 凭据和私钥访问控制。
- 主线 `ansible/` 没有调用 `AcmeConfig/`；`scripts/build-release.sh` 不打包它，主线
  `install.sh` 的签名验证也不覆盖它。根 README 却公开链接到该组件。
- `.github/workflows/env-check.yml` 和 `tests/verify-ansible.sh` 仍检查 AcmeConfig，
  因此当前是“CI 耦合、发布不耦合”的状态，而不是独立维护。
- `TODO.md` P0-1 中真实 CA 签发/续期、真实 DNS provider 日志审计、Ubuntu 22.04
  与真实消费者恢复均未验收。不能以自签临时 VM 测试代替这些门槛。

## 决策

**P0-1 真实环境门槛通过后，将 AcmeConfig 提取为独立仓库和独立签名 Release。**
当前先保持原目录及主线 CI 的安全检查，不把未验收的组件放进主线 Release，也不立即
从主线删除测试。Ansible role 暂不承载签发/续期实现；未来如需批量部署，只做薄适配层，
从固定版本、已验证身份和摘要的 ACME 资产安装，不能从可变分支拉脚本执行。

| 方案 | 取舍 |
| --- | --- |
| 继续靠根 README 链接维护 | 发布资产不包含 ACME，而 CI/文档却耦合；用户容易误认主线签名覆盖它。不选。 |
| 直接并入主线 Ansible role | 把 DNS 凭据、root 部署和证书续期生命周期绑进一次性机器初始化；测试与发布节奏不匹配。不选作实现主体。 |
| 独立仓库与签名 Release | 单独维护安全模型、版本和真实 CA 测试矩阵；需新增仓库控制面与迁移成本。选此方案。 |

## 执行顺序与验收

1. 先完成 `TODO.md` P0-1 的真实 CA、日志/权限、22.04 和消费者恢复证据；失败时
   继续保留“实验、不可用于生产”声明。
2. 盘点现有脚本调用、文档链接和 CI 引用；确定目标仓库的维护者、ruleset、
   release Environment、签名身份与秘密扫描。新仓库也必须满足与主仓库同等级的发布保护，
   不能因为拆仓降低安全性。
3. 在独立仓库发布首个带源码 SHA、固定依赖、SHA256 和 Sigstore 身份的版本；用
   Ubuntu 22.04/24.04 一次性 VM 验证安装、首次签发、续期、恢复与卸载。
4. 只在新资产和文档可独立使用后，从主仓库移走实现与 CI 专项检查；根 README 改为
   指向固定版本/独立文档，明确旧目录所在最后提交及支持边界。迁移前后均保留历史可追溯性。
5. 如确需 Ansible 批量管理，再新增仅消费固定签名资产的适配 role，并测试凭据不落入
   inventory、日志或 Ansible 事实缓存。此步不是拆仓的前置条件。

在第 4 步完成前，`TODO.md` 的 AcmeConfig 维护拆分项保持开放。独立仓库创建、远端保护
设置和首次 Release 属于新的远端状态变更，需另行确认范围；本决策本身不是执行授权。
